## 1. 背景：现状盘点（2026-10-28）

### 1.1 服务间调用全部经过 Dubbo

| 项 | 数量 | 说明 |
|---|---|---|
| Remote 接口（`tuoyu-api-*`） | 17 | system 12 个、resource 4 个、workflow 1 个；每个接口恰好一个实现 |
| `@DubboService` 实现 | 17 | system 12 个、resource 4 个、workflow 1 个（`RemoteWorkflowService`，**没有任何调用方**） |
| `@DubboReference` 注入点 | 38 | auth 13、workflow 15、system 1、框架模块 9；另有 1 处（workflow `SpelRuleComponent`）靠构造器注入借用了同一个引用 Bean |
| 带 Dubbo 专有行为的引用 | 2 | `OssUrlTranslationImpl` 的 `mock = "true"`（失败时返回空串）；`TokenController` 的 `stub = "true"`（吞掉推送消息的异常） |
| `@GlobalTransactional` | 0 | Seata 默认关闭，没有任何业务代码使用分布式事务 |
| 其他服务间调用（HTTP 客户端等） | 0 | 网关的 HTTP 转发不算服务间调用 |

调用关系（调用方 → 提供方）：

| 调用方 | 调用的接口 |
|---|---|
| auth | User、Social、Config、Client、Message（stub） |
| workflow | User、Dept、Role、Post、TaskAssignee、Dict、Message、Mail、Sms |
| system | Message（发布通知公告时推送） |
| 框架模块（被所有带它们的服务继承） | translation：User、Dept、File（mock）；log：Log、Client；mybatis（数据权限）：DataScope；service-impl：Dict、Permission |

**框架模块会“自己调自己”**：tuoyu-system 自身提供 User、Dept、Log、Client、DataScope、Dict、Permission，但它继承的框架 Bean 仍通过 `@DubboReference` 调用这些接口。仓库没有设置 `scope` / `injvm`，这些调用依靠 Dubbo 的默认行为，在本 JVM 内（injvm）完成。

### 1.2 上下文透传

| 上下文 | 现状 |
|---|---|
| 登录令牌 | 依靠依赖 `sa-token-dubbo3` 透传，仓库内没有自己的代码。提供方通过 Sa-Token 读取令牌中的信息，登录用户从 Redis 中的会话读取 |
| 数据权限 | `DubboDataPermissionFilter`（调用方）把 `DataPermissionHelper` 的上下文放进附件 `data:permission`；提供方没有显式读取它的代码 |
| 租户、链路 ID | 没有（多租户与链路追踪另行设计，见 ADR 0006、ADR 0007） |
| Seata XID | 依赖库中有过滤器，但 Seata 已关闭 |

### 1.3 不走 RPC 的跨服务通道

- **Spring Cloud Bus（自研的 Redis Stream 绑定器）**：workflow 发布 `ProcessEvent` 等 3 种远程事件，**仓库内没有监听者**，是留给业务模块的扩展点；
- **Redis 发布订阅**：resource 的 SSE / WebSocket 推送，在 resource 的多个实例之间扇出；其他服务通过 `RemoteMessageService` 调用 resource；
- **共享 Redis**：Sa-Token 会话、Spring Cache 的二级缓存。所有服务直接读写，不经过 RPC。

### 1.4 合并成单体时会撞上的问题

把 `tuoyu-modules/*` 装进一个 Spring 应用时，会冲突或行为改变的地方。本文先解决 RPC 相关的几项，其余在单体启动器中解决，见第 5 节：

| # | 问题 | 依据 |
|---|---|---|
| 1 | **只有网关校验登录**。服务只校验网关转发时带的 same-token，没有 `checkLogin`；很多接口没有 `@SaCheck*` 注解，完全依赖网关 | `SecurityConfiguration.java:41-53`，网关 `AuthFilter.java:54` |
| 2 | **URL 前缀由网关去掉**。网关把 `/system`、`/monitor`、`/resource`、`/auth`、`/tool`、`/workflow` 去掉后再转发，各服务的 Controller 挂在根路径；前端与少量代码（`GlobalExceptionHandler.java:133` 等）使用带前缀的路径。目前没有完全相同的路径冲突 | `tuoyu-gateway.yml:58-105` |
| 3 | **数据源都叫 `master`，但指向 3 个库**：system / resource / gen 指向 `tuoyu-cloud`，workflow 指向 `tuoyu-workflow`，job 指向 `tuoyu-job`；workflow 的 Mapper 没有 `@DS` | 各服务的 Nacos 配置 |
| 4 | **Flyway 只有一套 `spring.flyway.*`**：system 与 workflow 都在 `db/migration/{vendor}` 下放了 `V1__baseline.sql`，在同一个类路径下会冲突 | ADR 0004 |
| 5 | **本地缓存只在当前 JVM 失效**。Caffeine 一级缓存默认开启，没有跨 JVM 的失效广播；单体多实例部署时同样存在这个问题 | `PlusSpringCacheManager`、`CaffeineCacheDecorator` |
| 6 | **资源与配置重复**：每个服务都有自己的 `application.yml`、`logback-spring.xml`、`banner.txt`；很多配置以 `spring.application.name` 为键（日志目录、Redisson 客户端名、Bus 分组、Seata） | — |
| 7 | **JVM 级的静态状态与 `System.setProperty`**：SnailJob 执行器把日志 Appender 挂在根 Logger 上，并写入系统属性；Dubbo 写入注册 IP 的系统属性 | `SnailJobConfig.java:63-76` |
| 8 | **CORS 只在网关配置**；可信代理的默认值假设前面有网关 | `GatewayConfig.java:49-70` |
| 9 | **Sa-Token 监听器只在 auth 中**：system 踢下线用户时，不会清理 `online_tokens:*`。这在**微服务模式下就已经是问题**，见第 8 节 | `UserActionListener.java:20-45` |

## 2. 目标与非目标

**目标**

1. **同一份业务代码**：模块代码中不出现 Dubbo 的注解与 API，也不判断当前是哪种部署方式；
2. **单体**：跨模块调用是进程内的方法调用，不序列化，不经过网络，也不走本机的 HTTP；单体包中不包含 Dubbo；
3. **微服务**：跨服务调用仍走 Dubbo，注册中心、协议、端口、负载均衡与现在相同，可以逐个接口迁移；
4. **两种方式的行为一致**：业务能观察到的语义（事务边界、异常类型、参数校验、上下文）在两种方式下相同。确实无法相同的地方由抽象层处理，并写入本文；
5. **可验证**：规则由 ArchUnit 检查，两种方式的差异由测试覆盖。

**非目标（本阶段不做）**

- 分布式事务（Seata）：目前没有使用。跨服务调用的一致性按第 3.5 节的规则处理；
- 租户上下文透传：随多租户一起做（ADR 0006）。本文只预留透传接口（第 3.4 节）；
- 单体启动器 `tuoyu-boot-all` 与第 1.4 节的其余问题：之后实施（第 11 节）。本文只确定方向（第 5 节）；
- 改变注册中心、协议或序列化方式。

## 3. 决定

### 3.1 契约：`tuoyu-api-*` 只放接口与 DTO

- 跨模块调用**只能**通过 `tuoyu-api-*` 中的接口。模块不能依赖其他模块的实现类（ArchUnit，第 4 节）；
- 接口加上标记注解 **`@RemoteApi`**（位于 `tuoyu-common-rpc`，不依赖 Dubbo）。这个注解是“这是跨模块契约”的唯一标识，注入、导出、检查都以它为准；
- 参数与返回值**按值语义**使用：提供方不修改参数对象，调用方不修改返回的对象。在微服务方式下两边拿到的是序列化后的副本；在单体方式下是同一个对象，修改会互相影响（例如调用方修改了提供方缓存中的对象）。第一阶段审查现有 17 个实现中直接返回缓存对象的地方；
- DTO 必须实现 `Serializable`。字段校验注解（如 `RemoteUserBo` 上的 `@NotBlank`）由**提供方**校验（第 3.5 节）；
- `RemoteWorkflowService` 没有调用方，暂时保留接口，删除没有被使用的 `RemoteWorkflowServiceMock`。

### 3.2 提供方：普通的 Spring Bean，不再标注 `@DubboService`

- 实现类只是一个实现了 `@RemoteApi` 接口的普通 Spring Bean（`@Service`），不再出现 `@DubboService`；
- **微服务方式**：`tuoyu-common-dubbo` 中的导出器在启动时找出本服务中所有实现了 `@RemoteApi` 接口的 Bean，逐个导出为 Dubbo 服务。服务名、分组、版本与现在相同，所以迁移期间仍使用 `@DubboReference` 的调用方不受影响；
- **单体方式**：不导出（单体中没有 Dubbo）；
- 一个 `@RemoteApi` 接口在同一个容器中**只能有一个实现**，否则启动失败。

### 3.3 调用方：普通注入，“本地优先、否则远程”

> 最初的设想是业务代码统一用 `@RemoteReference` 注入，已确认改为**不需要任何注解的普通注入**（第 7 节 Q1）。

```java
@RequiredArgsConstructor
@Service
public class FlwTaskServiceImpl {
    private final RemoteUserService userService;   // 不加任何注解，构造器注入
}
```

`tuoyu-common-rpc` 在 Bean 定义阶段，为 classpath 中的每个 `@RemoteApi` 接口确定注入什么：

| 容器中有本地实现吗 | 部署方式 | 注入的是 |
|---|---|---|
| 有 | 任意 | **本地调用代理**（第 3.5 节），包装本地实现，标为 primary。微服务中 system 的框架 Bean“自己调自己”时，也从 Dubbo injvm 改为走这里 |
| 没有 | 微服务 | **Dubbo 引用**：由 `tuoyu-common-dubbo` 注册，超时、重试、负载均衡沿用现在的全局配置 |
| 没有 | 单体 | **启动失败**，并列出缺少实现的接口（说明单体包漏装了某个模块） |

选择普通注入的理由：

1. 业务代码与 Spring 的普通用法一致，构造器注入与 `final` 字段都能用，测试时直接传入模拟对象；
2. 注入什么完全由容器里有什么决定，与部署方式相关的判断只在 `tuoyu-common-rpc` 与 `tuoyu-common-dubbo` 中出现一次；
3. 不需要第二个注解，ArchUnit 只需要检查“模块中不出现 Dubbo”（第 4 节）。

部署方式由已有的配置项 **`tuoyu.deployment.mode`** 决定（`microservice` 默认 / `monolith`，首页已经在使用它）。单体包中没有 `tuoyu-common-dubbo`，配置成微服务时启动失败，避免配错。

### 3.4 上下文透传：一个 SPI，两种方式共用

`tuoyu-common-rpc` 定义透传接口，每一类上下文实现一次：

```java
public interface RpcContextPropagator {
    /** 调用方：取出要透传的值（只能是字符串，便于签名与审计） */
    Map<String, String> capture();
    /** 提供方：在执行前恢复，返回的句柄在执行后关闭，恢复调用前的状态 */
    AutoCloseable restore(Map<String, String> values);
}
```

- **微服务**：`tuoyu-common-dubbo` 中的一对过滤器调用这些实现，通过 Dubbo 附件传递；
- **单体**：调用在同一个线程中执行，上下文天然存在，本地调用代理**不做**传递。提供方不能修改调用方的上下文，例如调用 `DataPermissionHelper` 后要恢复原状；
- 迁移现有的两项：登录令牌（替换对 `sa-token-dubbo3` 的隐式依赖，两种方式下的行为都可以测试）与数据权限（`DubboDataPermissionFilter` 改为基于本 SPI，同时补上提供方的读取，并用测试确认它确实生效）；
- 之后加入租户（值带 HMAC 签名，提供方验签后才采信，见 ADR 0006）与链路 ID（ADR 0007）。

### 3.5 本地调用代理：让两种方式的语义一致

本地调用是进程内的方法调用（不序列化，不经过网络）。代理在调用前后只做以下几件事，让单体与微服务的行为一致：

| 语义 | 微服务（现状） | 单体：本地调用代理的处理 |
|---|---|---|
| **事务** | 提供方在自己的进程中执行，不参与调用方的事务 | **挂起调用方的事务**（相当于 `NOT_SUPPORTED`），提供方按自己的 `@Transactional` 开启新事务（已确认，第 7 节 Q2） |
| **异常** | Dubbo 默认的异常过滤器会把接口上没有声明、且与接口不在同一个 jar 中的异常（例如 `ServiceException`）包装成 `RuntimeException`，异常类型与错误码丢失（以第一阶段的验证为准） | 原样抛出。微服务方式也改为一致：`tuoyu-common-dubbo` 让 `org.tuoyu.common.core.exception` 下的异常原样传回 |
| **参数校验** | 调用方的 `validation: jvalidationNew` 校验 | 改为在**提供方**校验（实现类加 `@Validated`），两种方式相同；去掉调用方的 Dubbo 校验配置 |
| **超时与重试** | 超时 3 秒，不重试 | 没有超时。调用方不能依赖超时来中断调用 |
| **参数与返回值** | 序列化后的副本 | 同一个对象。按第 3.1 节的值语义规则使用；测试环境中可以打开“严格模式”，在代理中深拷贝参数与返回值，用来发现违反规则的代码 |

**事务语义选择“不参与调用方事务”的原因**：

1. 业务代码在单体中测试通过，到微服务中也应该成立。如果单体中跨模块调用共享事务，开发者很容易在不知不觉中依赖这种原子性，换成微服务后就会出现不一致；
2. 各模块可能连接不同的库（第 1.4 节第 3 条）。共享一个事务意味着共享一个数据库连接，后面的模块会在错误的库上执行；
3. 微服务中“自己调自己”的情况（现在通过 Dubbo injvm 在同一线程中执行，会加入调用方事务）也改为一致。

需要跨模块原子性的场景，按“本地事务 + 失败补偿”或“事务提交后发事件”实现（“本地消息表”在需要时再做）。

### 3.6 去掉 Dubbo 专有的 mock 与 stub

它们只在微服务方式下生效，在单体方式下行为不同：

- `OssUrlTranslationImpl`：在调用处捕获异常并返回空串，删除 `RemoteFileServiceMock`；
- `TokenController` 推送“欢迎登录”消息：在调用处捕获异常并记录日志，删除 `RemoteMessageServiceStub`。

### 3.7 模块划分

| 模块 | 内容 | 依赖 Dubbo |
|---|---|---|
| `tuoyu-common-rpc`（新，原创） | `@RemoteApi`、`RpcContextPropagator`、注入规则（第 3.3 节）、本地调用代理、部署方式的判定、启动时的检查（每个接口最多一个实现；单体中不能缺少实现） | 否 |
| `tuoyu-common-dubbo`（改造） | 导出器（第 3.2 节）、引用注册（第 3.3 节）、上下文过滤器（第 3.4 节）、异常原样传回（第 3.5 节）；保留现有的日志过滤器、IP 处理、元数据中心 | 是 |
| `tuoyu-api-*` | 只依赖 `tuoyu-common-core` 与 `tuoyu-common-rpc`（为了 `@RemoteApi`） | 否 |
| `tuoyu-modules/*` | 删除 `@EnableDubbo`、`@DubboService`、`@DubboReference` | 否 |
| `tuoyu-boot-*` | 组装：微服务启动器带 `tuoyu-common-dubbo`，单体启动器不带 | 仅微服务启动器 |

## 4. 依赖规则与检查

在 CI 中加入 ArchUnit 测试，规则如下：

1. `org.tuoyu.<模块>..`（模块代码）不能依赖 `org.apache.dubbo..`，也不能使用 `@DubboReference` / `@DubboService` / `@EnableDubbo`；
2. 模块之间只能通过 `org.tuoyu.*.api..` 访问，不能依赖其他模块的实现包；
3. `tuoyu-api-*` 中只能有带 `@RemoteApi` 的接口、DTO、事件与常量，不能有实现类；
4. `tuoyu-common-mybatis` 不依赖 `tuoyu-common-security`、`tuoyu-common-satoken`、`tuoyu-common-rpc`、Dubbo。现状中，数据权限上下文存放在 Sa-Token 的 `SaStorage` 中，并且有一个 Dubbo 过滤器，需要先完成下面的三个上下文 SPI；
5. `tuoyu-common-rpc` 与 `tuoyu-common-core` 不依赖 Dubbo；框架中只有 RPC 实现相关的模块（`tuoyu-common-dubbo`、负载均衡、Seata）使用 Dubbo，单体包中不包含 Dubbo；
6. `LoginHelper`（`tuoyu-common-satoken`）只在 `tuoyu-common-satoken` 与 `tuoyu-auth` 中使用：它处理登录、登出与会话，其他代码读取当前用户一律用 core 的 `UserContext`（ADR 0008）。

**三个上下文 SPI 与本文的关系**：当前用户（`UserContextProvider`，业务代码经静态入口 `UserContext` 读取，见 ADR 0008）、`PermissionContext`、`TenantContext` 定义在 `tuoyu-common-core` 中，由 `tuoyu-common-satoken` 等模块实现；后台任务使用“系统身份”实现。第 3.4 节的透传实现读写的就是这些上下文。所以实施顺序是：先完成三个上下文 SPI，再迁移上下文透传，最后满足规则 4。

**精简模块**：示例模块已删除，AI 模块已移入 `tuoyu-extensions`。只需要确认可选扩展模块也遵守规则 1、2（AI 扩展目前没有使用 Dubbo）。

## 5. 单体方式的方向（本节只确定方向，实施见第 11 节）

对应第 1.4 节的问题：

| # | 方向 |
|---|---|
| 1 登录校验 | **登录校验下沉到各服务**：框架过滤器执行 `checkLogin`，加上客户端校验，白名单从网关配置移到公共配置。在微服务方式下也成为第二道防线：内网请求即使绕过网关，也必须登录。**在 RPC 迁移的最后做**（已确认，Q4），不等单体启动器 |
| 2 URL 前缀 | 单体按 Controller 所在的包加前缀（Spring MVC 的 `addPathPrefix`），前缀表与网关路由使用同一份配置，前端在两种方式下的 URL 完全相同 |
| 3 数据源 | **单体保持与微服务相同的库划分**（已确认，Q3）：`tuoyu-cloud`、`tuoyu-workflow`、`tuoyu-job` 仍是三个库，部署方式切换时数据不用迁移。每个模块的 Mapper 按包路由到自己的数据源（`system`、`workflow` 等，不再都叫 `master`）；跨模块调用不共享事务（第 3.5 节），所以不会在错误的库上执行 |
| 4 Flyway | 每个库一套迁移目录与独立的迁移记录表（例如 `db/migration/workflow/{vendor}`），单体中依次执行。ADR 0004 届时修订 |
| 5 本地缓存 | 单体单实例时不受影响；多实例（两种方式都有）的一级缓存失效广播在 1.1 做。1.0 的文档要说明多实例部署的影响：其他实例的一级缓存要等过期（30 秒）后才会读到新值 |
| 6 资源与配置 | 启动器提供唯一的 `application.yml`、`logback`、`banner`；模块中的这些文件改为可合并的命名配置 |
| 7 静态状态 | 逐项改为容器管理的 Bean，或确认单体中只初始化一次 |
| 8 CORS、可信代理 | CORS 改为框架可选配置（单体开启，微服务由网关负责） |
| 9 Sa-Token 监听器 | 移到框架中，所有服务都注册（这个问题在微服务方式下就已存在，见第 8 节） |
| 10 定时任务 | **单体包含定时任务**（已确认，Q5）。现状：任务执行器在 `tuoyu-job` 中（9 个 SnailJob 执行器），调度由独立的 SnailJob 服务端（`tuoyu-snailjob-server`，自带数据源、Web 上下文 `/snail-job`、Netty 端口与管理界面）负责。实施时先做技术验证，按以下顺序选定形式：① 把 SnailJob 服务端装进单体进程，用**独立的子容器**隔离它的 Bean 与配置（保留管理界面、日志与重试，仍是一个 JVM）；② 不可行时，单体包含执行器，SnailJob 服务端作为第二个进程随单体一起部署（compose 中默认启用）。不自己编写调度器（超出 1.0 范围）。执行器挂在根 Logger 上的日志 Appender（第 1.4 节第 7 条）在单体中会收集所有模块的日志，改为只收集任务执行期间的日志 |

## 6. 实施计划

### 第一阶段：用 system 与 resource 验证

1. 新建 `tuoyu-common-rpc`，改造 `tuoyu-common-dubbo`（第 3.7 节），**先写测试**：
   - 注入规则：有本地实现时注入本地代理；没有时，微服务注入 Dubbo 引用、单体启动失败；同一接口有两个实现时启动失败；
   - 本地代理：挂起事务、原样抛出异常、严格模式下拷贝参数与返回值；
   - 两种方式的对照测试：在同一个 JVM 中启动两个 Spring 容器，用 Dubbo 直连（不经过注册中心）互相调用，与单体（一个容器）运行同一组用例，比较结果；
2. `tuoyu-api-system` 与 `tuoyu-api-resource` 的接口加 `@RemoteApi`；system 的 12 个、resource 的 4 个实现去掉 `@DubboService`，由导出器导出；
3. 迁移这两个服务之间的调用：system 发布通知公告时推送（`RemoteMessageService`），以及两个服务各自的框架 Bean“自己调自己”（translation、log、数据权限、字典、权限）；
4. 验证第 3.5 节表格中两处“以验证为准”的内容（异常包装、injvm 的行为），把结论写回本文；
5. 本机启动 4 个核心服务，冒烟测试：登录、字典、部门树、数据权限、通知推送、文件链接翻译；
6. **评审**：评审通过后进入铺开阶段；不通过时修订本文，不铺开。

### 之后：铺开

1. 迁移 auth（13 处）、workflow（15 处）与其余框架模块的引用；删除 mock / stub（第 3.6 节）；去掉各启动类的 `@EnableDubbo`；
2. 三个上下文 SPI；第 3.4 节的透传改为基于它们；
3. ArchUnit 规则进入 CI，现有代码全部满足；
4. **登录校验下沉到各服务**（第 5 节第 1 条，Q4）：先补测试，覆盖“未登录访问没有注解的接口被拒绝”“白名单接口可以访问”“经网关的请求行为不变”；同时把 Sa-Token 监听器移到框架中（第 8 节）；
5. 更新 CONTRIBUTING.md（新增“跨模块调用”一节，写明第 3.1、3.5 节的规则）与代码生成模板（生成的服务代码不出现 Dubbo）。

**完成标准**：模块代码中没有 Dubbo 的注解与 API；ArchUnit 规则在 CI 中通过；两种方式的对照测试覆盖全部 17 个接口中的代表性方法；各服务自行校验登录；4 个核心服务的冒烟测试通过。

## 7. 决定（2026-10-28 维护者确认）

| # | 问题 | 决定 | 备注 |
|---|---|---|---|
| Q1 | 调用方的注入方式 | 普通构造器注入，不加注解（第 3.3 节） | 最初设想用 `@RemoteReference` |
| Q2 | 单体中跨模块调用的事务 | 两种方式都**不参与**调用方事务（第 3.5 节） | 最初设想单体中使用本地事务 |
| Q3 | 单体使用几个库 | 保持与微服务相同的库划分（第 5 节第 3 条） | — |
| Q4 | 登录校验下沉到各服务的时机 | RPC 迁移的最后做，微服务方式下也生效（第 6 节铺开第 4 步） | — |
| Q5 | 单体是否包含定时任务 | **包含**。形式在实施单体启动器时经技术验证后确定：优先把 SnailJob 服务端装进单体进程的独立子容器，不可行时作为第二个进程随单体部署（第 5 节第 10 条） | 与“最小部署 1 个 JVM”的目标相关：如果只能用第二个进程，需要修订该目标 |

## 8. 盘点中发现的现有问题（与本文无关，单独处理）

- system 踢下线用户（`SysUserOnlineController`）时不会触发 auth 中的 `UserActionListener`，`online_tokens:*` 中的记录要等过期才会消失（第 1.4 节第 9 条）；
- 很多接口没有 `@SaCheck*` 注解，只依赖网关的登录校验（第 1.4 节第 1 条）。在微服务方式下，有 same-token 保护，不能直接从内网访问；

## 9. 后果

- 模块代码不再依赖 Dubbo，切换 RPC 实现（例如改用 Triple 协议或 HTTP）只影响 `tuoyu-common-dubbo`；
- 单体与微服务的跨模块调用语义一致，代价是单体中不能依赖跨模块的事务原子性；
- 微服务方式下“自己调自己”从 Dubbo injvm 改为直接调用，减少一层 Dubbo 处理；
- 迁移可以逐个接口进行：迁移期间，导出器导出的服务与仍使用 `@DubboReference` 的调用方兼容；
- 新增依赖：无（只使用 Spring 与 Dubbo 已有的 API）。

## 10. 实施记录（2026-10-29）

按本文实现，以下是实施中的结论与调整：

| 项 | 结果 |
|---|---|
| 迁移范围 | 17 个接口加 `@RemoteApi`；17 个实现去掉 `@DubboService`；38 处 `@DubboReference` 全部改为构造器注入；6 个启动类去掉 `@EnableDubbo`；删除 `RemoteFileServiceMock`、`RemoteMessageServiceStub`、`RemoteWorkflowServiceMock`，改为在调用处捕获异常（`OssUrlTranslationImpl`、`TokenController`） |
| 第 3.5 节“以验证为准”的两处 | **已证实**：Dubbo 3.3 默认以 STRICT 模式检查反序列化，`ServiceException` 不在白名单中，原来能传回是因为默认的 exception 过滤器把它包装成了 JDK 的 `RuntimeException`（错误码随之丢失）。现在 `tuoyu-common-dubbo` 登记了白名单 `security/serialize.allowlist`（只放行 `org.tuoyu.common.core.exception.`），并以 `RemoteExceptionFilter` 取代默认过滤器（`dubbo.provider.filter: -exception`），框架异常连同错误码原样到达调用方 |
| 上下文透传接口位置 | 由 `tuoyu-common-rpc` 改放到 `tuoyu-common-core`（`ContextPropagator`、`ContextPropagators`）：同一套实现还用于跨线程（`@Async` 的 `TaskDecorator`、`ThreadUtils` 的虚拟线程），框架模块实现它时不必依赖 RPC 模块（满足第 4 节规则 4） |
| 透传值的编码 | 全部上下文放在一个 Dubbo 附件 `tuoyu-context` 中（`k=v&k=v`，URL 编码），避免不同协议对附件键大小写的处理不同；值只能是字符串 |
| 登录令牌的透传 | **保留** `sa-token-dubbo3`（只在 `tuoyu-common-dubbo` 中，业务代码不依赖它）：它同时为 Dubbo 线程提供 Sa-Token 的上下文，自己重写没有收益。第 3.4 节中“迁移登录令牌”改为此做法 |
| 数据权限的透传 | `DubboDataPermissionFilter` 删除；`DataPermissionPropagator` 只透传“是否忽略数据权限”和“接口的访问要求”两项字符串，当前用户在提供方从令牌重新读取。原来把整个登录用户对象放进附件，并借 Sa-Token 的存储在线程间传递 |
| 上下文 SPI 与 ORM 层的依赖 | `tuoyu-common-core` 新增当前用户（静态入口 `UserContext`，实现方提供 `UserContextProvider`，见 ADR 0008）、`PermissionContext`、`TenantContext`、`DataScopeService`；Sa-Token 模块实现前两个；`tuoyu-common-mybatis` 只依赖 core（不依赖 Sa-Token、`tuoyu-api-system`、Dubbo） |
| 依赖规则检查 | 新增只含测试的模块 `tuoyu-architecture`（ArchUnit 1.4.1，Apache-2.0），读取各模块编译后的类检查第 4 节的规则，放在构建顺序的最后。现有代码没有违规，不需要“待清理名单” |
| 登录校验下沉（第 5 节第 1 条） | `tuoyu-common-satoken` 新增 `RequestAuthenticator`（白名单、登录、客户端 ID、客户端路径与 IP 规则），网关与各服务共用；各服务在 same-token 通过后按 `X-Forwarded-Prefix` 还原完整路径再校验；白名单移到 `application-common.yml`。Sa-Token 监听器中清理在线记录的部分移到框架（`OnlineTokenCleanupListener`），修正第 8 节第 1 条 |

## 11. 单体启动器实施记录（2026-10-30）

按第 5 节实现单体启动器 `tuoyu-boot/tuoyu-boot-all`（原创编写）。以下是各项的落地方式与对第 5 节的调整：

| 第 5 节 | 实现 |
|---|---|
| 模块划分（第 3.7 节） | 微服务方式仍由各业务模块自己启动，**不新增 `tuoyu-boot-<服务名>`**：把业务模块拆成“库 + 启动器”要搬动全部启动类、配置、Dockerfile 与 IDEA 启动配置，收益只是微服务包中少一层依赖。改为：业务模块的可执行 jar 带 `exec` 后缀（`target/<模块>-exec.jar`），普通 jar 供单体依赖；单体在 pom 中排除 `tuoyu-common-dubbo`、`tuoyu-common-seata`、Dubbo、Spring Cloud Alibaba（Nacos、Seata），`MonolithAssemblyTest` 检查类路径中没有它们 |
| 启动类 | `TuoYuBootAllApplication` 扫描 `org.tuoyu.{boot,auth,system,resource,workflow,gen,job}`，排除各模块自己的 `@SpringBootApplication` 启动类 |
| 2 URL 前缀 | `ModulePathPrefixConfiguration` 用 Spring MVC 的 `addPathPrefix` 按包加前缀，前缀表在 `tuoyu-boot-all.yml` 的 `tuoyu.monolith.path-prefixes`。“前缀表与网关路由使用同一份配置”改为由 `ModulePathPrefixConsistencyTest` 校验两者一一对应：网关是路由规则，单体是包规则，写在一处反而难懂。消息推送（SSE）的 Controller 在框架模块 `tuoyu-common-push` 中，登记在 `/resource` 下；Warm-Flow 设计器在网关中不去掉前缀，单体中不需要登记 |
| 3 数据源 | 单体的数据源为 `master`（tuoyu-cloud）与 `workflow`（tuoyu-workflow）。`ModuleDataSourceAdvisor` 在调用某个模块的组件（`@Component` 及其衍生注解，配置类与 final 类除外）时切换到该模块的数据源，调用结束后恢复；路由表在 `tuoyu.monolith.datasource-routes`。它排在事务切面与 `@DS` 切面之前（`spring.datasource.dynamic.aop.order` 调为最高优先级 + 1），所以事务取到的是正确的连接，显式的 `@DS` 仍然生效。第 5 节写的是“Mapper 按包路由”，实际改为按组件路由：事务在进入 Service 时就取了连接，只在 Mapper 上切换来不及。跨模块调用经过本地调用代理（挂起调用方事务）后进入提供方的组件，在这里切换，所以访问数据库的模块都要登记，未登记的组件（框架组件）沿用调用方的数据源。启动时检查路由中的数据源都已配置 |
| 4 Flyway | 迁移脚本按库分目录：`db/migration/<库名>/{vendor}`（cloud、workflow、job），库名由负责服务的 `tuoyu.flyway.database` 指定（写在服务自己的 `application.yml` 中）。脚本只是移动目录，内容与校验和不变，已接入的库不受影响。单体中主库由 `spring.flyway.*` 连接，工作流库写在 `tuoyu.flyway.additional.workflow`，在主库之后用同样的约定迁移，各库有自己的迁移记录表（表名相同、在各自的库中）。ADR 0004 随之修订 |
| 5 本地缓存 | 未改动，按原结论在文档中说明多实例部署的影响 |
| 6 资源与配置 | 单体自带 `application.yml`、`logback-spring.xml`、`banner.txt`（单体模块的资源在类路径中排在最前）。配置与微服务方式是同一套文件：单体从 `TUOYU_CONFIG_DIR`（默认 `deploy/config/nacos`）依次导入 `application-common.yml`、`datasource.yml` 与各模块的配置，最后导入单体专用的 `tuoyu-boot-all.yml`（部署方式、数据源、迁移、入口相关的配置）。**单体不需要 Nacos** |
| 7 静态状态 | SnailJob 执行器挂在根 Logger 上的日志 Appender 只在任务执行线程中上报（它先检查任务的日志上下文，没有时直接返回），单体中不会收集其他模块的日志，不需要修改。`SnailJobConfig` 改为可选注入 `DiscoveryClient`：单体没有注册中心，按 `snail-job.server.host`（`TUOYU_SNAILJOB_SERVER_HOST`）直连 |
| 8 CORS、可信代理 | 单体是入口：可信代理沿用网关的默认值（`TUOYU_GATEWAY_TRUSTED_PROXIES`，只信任回环）；不校验 same-token。**同时修正一个问题**：服务原来无条件采信 `X-Forwarded-Prefix` 来还原完整路径，不校验 same-token 时（单体，或关闭了 same-token 的微服务）客户端可以伪造这个头，把受保护的路径拼成白名单中的路径。现在只有 same-token 校验开启时才采信它（`SecurityConfiguration.requestPath`）。跨域默认关闭，`TUOYU_CORS_ALLOWED_ORIGINS` 列出允许的来源时开启，不允许 `*` |
| 9 Sa-Token 监听器 | RPC 迁移时已移到框架（第 10 节） |
| 10 定时任务 | 单体包含任务执行器（tuoyu-job）。SnailJob 服务端在 1.0 中**作为第二个进程随单体部署**（compose 中默认启用，即第 5 节的方案②）。方案①（装进单体进程的独立类加载器）需要连接数据库实际运行才能验证，尚未完成，见下方“尚未验证” |
| 内嵌注册中心 | 不做。Nacos 服务端是完整的 Spring Boot 应用，自带的 Spring Boot、Jetty / Tomcat、gRPC、Jackson 等版本与本项目不同，放进同一个类路径必然冲突，只能另起类加载器或进程；体积约 100MB、内存约 512MB；微服务至少 4 个进程，内嵌在其中一个里会让其他服务依赖它先启动。免装 Nacos 由单体提供；微服务方式下 `./dev up` 用 compose 一键启动 Nacos |
| 冒烟测试（2026-10-30） | 单体连接 MySQL 与 Redis 启动，`tuoyu-e2e` 21 项通过（包括工作流读取自己的库）。过程中发现并修正了两个问题：Flyway 此前从未执行迁移（`{vendor}` 未替换，ADR 0004 已修订）；关闭多租户时新增数据插入 null 的 `tenant_id` |

**测试**：`ModulePathPrefixConsistencyTest`（前缀表与网关路由一致、更具体的包在前）、`ModuleDataSourceAdvisorTest`（按包切换与恢复、跨模块切换、异常时恢复、仓库配置的路由）、`MonolithAssemblyTest`（类路径中没有 Dubbo / Nacos / Seata；每个 `@RemoteApi` 在单体中有且只有一个实现；导入的配置文件存在）、`ProductionConfigTest` 新增单体组合配置的生产检查、`MigrationScriptsTest` 新增单体的迁移配置检查、`SecurityConfigurationPathTest`。
