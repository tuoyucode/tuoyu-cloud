# ADR 0004：数据库迁移与 Excel 导出 / 导入行数上限

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（2026-10-28）；同日修订：1.0 同时支持 MySQL 与 PostgreSQL；2026-10-30 修订：迁移目录按库划分，单体在一个进程中迁移多个库（ADR 0005 第 11 节） |
| 适用 | 后端新模块 `tuoyu-common-flyway`；`tuoyu-system`、`tuoyu-workflow`、`tuoyu-snailjob-server`（迁移负责服务）；`tuoyu-common-excel`、`tuoyu-common-mybatis`（`PageQuery.countOnly()`）、全部导出接口与用户导入；代码生成的后端模板 |

## 1. 数据库迁移

### 1.1 背景

改造前没有任何迁移机制：全新安装执行 `deploy/sql` 下的完整脚本，已有数据库由运维按日期手工执行 `deploy/sql/upgrade` 下的升级脚本。升级是否执行完全靠人记，跨版本升级容易漏。

因此接入 Flyway。1.0 同时支持 MySQL 与 PostgreSQL，Oracle 不在 1.0 的支持范围内，仍用升级目录手工维护。

### 1.2 每个库由一个服务负责

盘点各服务连接的库（`deploy/config/nacos/datasource.yml` 与各服务配置）：

| 库 | 连接它的服务 | 负责迁移 |
|---|---|---|
| `tuoyu-cloud` | `tuoyu-system`、`tuoyu-resource`、`tuoyu-gen` | **`tuoyu-system`** |
| `tuoyu-workflow` | `tuoyu-workflow` | **`tuoyu-workflow`** |
| `tuoyu-job` | `tuoyu-snailjob-server`（`spring.datasource`）、`tuoyu-job`（执行器，`datasource.job`） | **`tuoyu-snailjob-server`** |
| `tuoyu-ai` | 可选扩展 | 1.0 不接入 |

`tuoyu-job` 库的选择与最初设想（由 `tuoyu-job` 负责）不同，理由：

- 库里只有 SnailJob 服务端的 `sj_*` 表，服务端启动时就要读写这些表；执行器 `tuoyu-job` 通过 Netty 与服务端通信，不读写这些表；
- 表结构与 SnailJob 服务端的版本绑定，升级 SnailJob 时的结构变更应由服务端负责；
- 如果由执行器负责，执行器没启动时服务端在空库上无法启动。

一个库只有一个负责服务，避免多个服务同时迁移同一个库、互相争抢迁移锁或重复建表。`MigrationScriptsTest` 校验：只有这三个模块带迁移脚本、依赖 `tuoyu-common-flyway`、在 Nacos 配置中出现 `spring.flyway`，且迁移地址指向各自负责的库。

`tuoyu-resource`、`tuoyu-gen` 也连接 `tuoyu-cloud` 库：在空库上应先启动 `tuoyu-system`（核心服务的启动顺序本来就是 system 在前）。

### 1.3 基线与增量

- 每种数据库一套脚本，放在负责服务的 `src/main/resources/db/migration/<库名>/mysql/` 与 `db/migration/<库名>/postgresql/`（库名为 `cloud`、`workflow`、`job`，由负责服务 `application.yml` 中的 `tuoyu.flyway.database` 指定。按库分目录是为了单体：几个库的脚本在同一个类路径下，不能互相混淆），命名 `V<版本>__<小写说明>.sql`，版本各自从 1 开始连续。同一个改动在两套中使用相同的版本号与说明，内容按各自的方言编写；
- **V1 基线**（`V1__baseline.sql`）= 接入时 `deploy/sql` 下同一数据库的全新安装脚本（MySQL：`tuoyu-*.sql`；PostgreSQL：`postgres/postgres_tuoyu_*.sql`），逐字一致（只统一了换行符）；
- 之后表结构或种子数据改动**只写成新的迁移脚本**（`V2__xxx.sql` 起），两种数据库各写一份。V1 与全新安装脚本都不再修改；
- 三种起点都会到达同一个结果：

| 起点 | 启动负责服务时 |
|---|---|
| 空库 | 依次执行 V1、V2…… |
| 用 `deploy/sql` 的全新安装脚本初始化的库（= V1） | 按基线版本 1 接入，执行 V2 起的脚本 |
| 接入前已在运行的库 | 同上。**首次启用前，必须先执行完 `deploy/sql/upgrade` 下的全部升级脚本**，使库达到 V1 状态 |

“已有表但没有迁移记录表”的库按基线版本 1 接入（`baselineOnMigrate`），Flyway 在库中新建 `flyway_schema_history` 记录版本。

接入前先核对（`SupportedDatabaseMigrationStrategy`，失败闭合）：从类路径中对应数据库的 `V1__baseline.sql` 取出全部建表语句的表名，库中必须都已存在（不区分大小写；MySQL 按当前库、PostgreSQL 按当前 schema 列出），缺少时拒绝启动，并列出缺少的表、提示先执行 `deploy/sql/upgrade` 下的升级脚本或检查数据源是否连错库。这样可以避免两种静默错误：库里只有几张无关的表时被直接标记为 V1、业务表永远不会创建；旧库表结构未补齐时被当作 V1、之后再也不会补。基线之外的表（例如旧版本遗留的 `test_leave`）只记警告。表结构以外的差异（种子数据）无法这样核对，仍需按升级目录的说明先执行升级脚本。

否决的方案：继续在原处修改全新安装脚本，并要求每个增量脚本可重复执行。这样全新安装脚本与迁移脚本是两份独立维护的内容，无法在不连库的情况下验证两者一致；冻结 V1 后两者天然一致，测试可以逐字比对。

### 1.4 框架固定的约定

`tuoyu-common-flyway` 在 `spring.flyway.*` 配置之后应用以下约定（`FlywayConventions`），配置无法改变：

| 项 | 取值 | 理由 |
|---|---|---|
| 迁移目录 | `classpath:db/migration/<库名>/{vendor}` | 库名来自 `tuoyu.flyway.database`（未配置或不规范时拒绝启动）。`{vendor}` 由迁移策略按连接的数据库替换为 `mysql` 或 `postgresql`：Flyway 本身不认识它，只有 Spring Boot 读取 `spring.flyway.locations` 时才替换，而本约定是直接设置目录（2026-10-30 发现此前从未替换，迁移一直没有执行）。替换后类路径中没有该库的 V1 基线时拒绝启动 |
| `baselineOnMigrate` / `baselineVersion` | `true` / `1` | 已有数据库按 V1 接入 |
| `cleanDisabled` | `true` | 禁止 clean（清空整个库），防止误操作删除生产数据 |
| `placeholderReplacement` | `false` | 种子数据中有 `${initiator}` 这类业务表达式，必须原样写入；开启替换会导致迁移失败 |
| `outOfOrder` | `false` | 不允许补执行比当前版本小的脚本 |
| `validateOnMigrate` / `validateMigrationNaming` | `true` | 已执行脚本被修改、命名不规范时拒绝启动 |

单体在一个进程中负责多个库（ADR 0005 第 11 节）：主库由 `spring.flyway.*` 连接，其他库写在 `tuoyu.flyway.additional.<库名>`（`url`、`user`、`password`），在主库之后按同样的约定与策略依次迁移，迁移记录表在各自的库中。

只对支持的数据库执行迁移（`SupportedDatabaseMigrationStrategy`）：迁移前读取 JDBC 元数据中的数据库产品名，不是 MySQL 或 PostgreSQL 时（例如 Oracle、MariaDB）记录警告并跳过，不建迁移记录表，也不做基线；连接失败时拒绝启动。

### 1.5 配置

负责服务的 Nacos 配置（`tuoyu-system.yml`、`tuoyu-workflow.yml`、`tuoyu-snailjob-server.yml`）：

```yaml
spring:
  flyway:
    enabled: ${TUOYU_FLYWAY_ENABLED:true}
    url: ${datasource.<数据源名>.url}
    user: ${datasource.<数据源名>.username}
    password: ${datasource.<数据源名>.password}
```

- Flyway 使用单独的连接（`SimpleDriverDataSource`，不进入连接池），不经过动态数据源和 Seata 代理；
- 迁移在 MyBatis 等访问数据库的组件初始化之前完成（Spring Boot 的数据库初始化依赖检测，MyBatis-Plus 已登记）；
- `TUOYU_FLYWAY_ENABLED=false` 可关闭（例如由 DBA 统一执行脚本）。关闭后，新增的迁移脚本需手工执行；
- 数据库类型由 `TUOYU_DB_TYPE` 选择（`mysql` 默认，或 `postgresql`）：`datasource.yml` 按它拼出各库的连接地址（格式、默认端口、参数）并选择驱动，各服务的数据源与迁移地址随之切换。PostgreSQL 的库名与 MySQL 相同（`tuoyu-cloud` 等，含连字符，建库时需加双引号）。

### 1.7 测试

`MigrationScriptsTest`（不连库，不依赖 Docker）：

1. 命名规范与版本连续；
2. 两种数据库的 V1 都与对应的全新安装脚本逐字一致，且 SHA-256 与发布时记录的值一致（防止两份同时被改）；
3. 每个脚本都能被 Flyway 对应数据库的解析器（`MySQLParser`、`PostgreSQLParser`）完整切分成语句，且不切换、创建或删除数据库；
4. 迁移负责关系（见 1.2 节）与 Nacos 中的迁移地址；`TUOYU_DB_TYPE=postgresql` 时迁移地址与驱动随之切换。

`MigrationIntegrationTest`（Testcontainers，需要 Docker）：在真实的 MySQL（`mysql:8.4.9`，启动参数与 `deploy/docker/docker-compose.yml` 一致）与 PostgreSQL（`postgres:14.2`）上，按服务启动时的做法（`FlywayConventions` + `SupportedDatabaseMigrationStrategy`，连接参数与 `datasource.yml` 一致）执行每个负责服务的迁移脚本。负责服务按目录自动发现，新增库无需改测试：

1. 空库：从 V1 执行到最新版本，再次迁移不执行任何脚本，校验通过；
2. 已有库（执行过全新安装脚本、没有迁移记录表）：按基线 1 接入，只执行 V2 起的脚本；
3. 有表但缺少基线中的表：拒绝迁移，也不建迁移记录表。

本机没有 Docker 时跳过；CI（`CI=true`）中必须执行，没有 Docker 时失败，不会悄悄跳过。为了让测试能指定“只看某个服务的迁移脚本”，`SupportedDatabaseMigrationStrategy` 从 Flyway 配置的类加载器读取基线脚本（与 Flyway 查找迁移脚本的来源一致；服务中两者相同）。

PostgreSQL 的运行时支持（MyBatis 方言、代码生成、工作流、SnailJob）沿用框架已有的多数据库设计（例如 `DataBaseHelper.findInSet`），迁移测试只覆盖表结构与种子数据，**运行时仍未在真实 PostgreSQL 上验证**。

### 1.8 后果

- 维护者修改表结构或种子数据时，为 MySQL 与 PostgreSQL 各写一份迁移脚本；Oracle 仍改全新安装脚本并在 `deploy/sql/upgrade` 下新增升级脚本（见该目录的 README）；
- `deploy/sql` 下 MySQL 与 PostgreSQL 的全新安装脚本停留在基线版本，手工安装的部署方在其后需要执行（或由服务自动执行）V2 起的迁移脚本；
- 将来重新生成基线（例如 2.0）时另立 ADR。

## 2. Excel 导出 / 导入行数上限

### 2.1 背景（盘点结果）

导出接口共 11 个，其中 10 个是 Excel 列表导出，全部“查出全部数据再写文件”，没有行数上限：

| 服务 | 接口 |
|---|---|
| `tuoyu-system` | 登录日志、操作日志、客户端、参数、字典类型、字典数据、岗位、角色、用户 |
| `tuoyu-workflow` | 流程分类 |

第 11 个是流程定义导出（`/workflow/definition/exportDef/{id}`），只导出一条定义，不受影响。

Excel 导入只有用户导入（`/system/user/importData`）。它的监听器每读一行就写库一次，不在事务中；如果读到一半才发现超限，前面的行已经导入了。流程定义导入（`importDef`）是 JSON，不在此列。

### 2.2 规则（已确认：超限时拒绝并提示，不截断）

| 项 | 默认 | 配置 | 提示 |
|---|---|---|---|
| 导出 | 50000 行 | `tuoyu.excel.max-export-rows` | 导出数据超过 50000 行，请缩小查询范围后重试 |
| 导入 | 5000 行 | `tuoyu.excel.max-import-rows` | 导入数据超过 5000 行，请拆分为多个文件后重试 |

- 取值 1 ~ 1000000（单个工作表最多 1048576 行），不合理时拒绝启动；Nacos 刷新后生效；
- `ProductionConfigTest` 校验仓库配置中导出不超过 100000、导入不超过 10000；安全中心展示当前上限。

### 2.3 实现（`tuoyu-common-excel`）

**导出：先统计，再查询。**`ExcelBuilder.query(counter, loader, Vo.class)` 先执行统计，超限直接抛出业务异常，不执行查询；查询后再按实际行数校验一次（统计与查询之间可能有新数据写入）。`ExcelBuilder.of(list, ...)` 写出前也会校验，作为没有先统计的导出的兜底（返回提示而不是半个文件）。模板导出同样校验。

统计用 `PageQuery.countOnly()`（第 1 页、每页 1 行）：分页插件执行的 COUNT 语句会去掉 ORDER BY，租户与数据权限条件照常生效，与列表的结果一致。没有直接用 `selectCount`：各服务的查询条件里带 ORDER BY，`SELECT COUNT(*) ... ORDER BY` 在 PostgreSQL 上会报错。用户导出按原查询（关联部门与负责人、数据权限）新增了 `SysUserMapper.countUserExportList`。

**导入：先预读统计，再正式读取。**`ExcelBuilder.read(InputStreamSource, ...)`（`MultipartFile` 即是）先读一遍只计数，超限时一行都不处理；未超限再正式读取。正式读取时计数器最先注册，再计一次，兜底只能读一遍的 `read(InputStream, ...)`（它在读到超出的那一行时终止，之前的行可能已被处理，因此逐行写库的导入必须传文件本身）。单元格转换失败的行同样计数；计数器不处理其他异常，原有的“快速失败 / 收集错误”行为不变。

**代码生成**：后端模板开启导出时生成 `countList`，导出接口使用 `ExcelBuilder.query`。

### 2.4 已知限制

- 未超限的导出仍会把数据一次性读入内存（最多 50000 行）；需要更大数据量的导出应改为异步任务 + 分批写出，不在 1.0 范围内；
- `ExcelWriterWrapper`（自定义分批写出）不计数，由调用方自行控制行数。
