# ADR 0003：上传、XSS、脱敏与字段加密

| 项 | 内容 |
|---|---|
| 状态 | 已采纳（2026-10-28） |
| 适用 | 后端 `tuoyu-common-core`（上传校验）、`tuoyu-resource`（OSS 上传与下载）、`tuoyu-common-web`（富文本、响应增强）、`tuoyu-common-sensitive`、`tuoyu-common-encrypt`（字段加密）、`tuoyu-system`（通知公告）；前端富文本展示 |

## 1. 背景（盘点结果）

### 1.1 上传

全仓库对外的上传入口只有 `tuoyu-resource` 的 `POST /oss/upload`（头像、附件、富文本里的图片都走它），另有 `SysOssServiceImpl.upload(File)` 供服务内部调用。用户导入（`/system/user/importData`）与流程定义导入（`/workflow/definition/importDef`）只在内存中解析，不落盘、不对外提供下载，不在本次范围内。

旧实现的问题：

1. **不校验类型**：任何扩展名都能上传，包括 `.html`、`.svg`、`.exe`、`.jsp`；
2. **采信客户端的 Content-Type**：上传时把客户端声明的类型原样写入对象存储；公开桶直接访问时，浏览器会按 `text/html` 渲染，构成存储型 XSS；
3. **对象键沿用原始扩展名**（含大小写与任意后缀）；
4. 下载接口按存储中记录的类型返回，没有 `X-Content-Type-Options: nosniff`；
5. `MimeTypeUtils.DEFAULT_ALLOWED_EXTENSION` 中有 `html`、`htm`，但没有任何地方使用它。

### 1.2 XSS

旧实现是全局过滤器（`XssFilter` + `XssHttpServletRequestWrapper`）：对 POST / PUT 请求的参数与 JSON 请求体做“删除 HTML 标签”。问题：

1. **修改用户输入**：`a<b` 这类正常文本被改写，JSON 请求体是整体按字符串处理的，字段值之外的内容也可能被改坏；
2. **该防的没防住**：唯一真正保存 HTML 的通知公告（`/system/notice`）在排除名单里，公告内容完全不清洗，有公告权限的人可以写入脚本；
3. GET、DELETE 不处理，按路径排除，规则分散；
4. 防 XSS 的正确位置是输出：前端（Vue / Ant Design Vue）默认对文本转义，只有 `v-html` 才会渲染 HTML。

### 1.3 脱敏

`tuoyu-common-sensitive` 在响应输出前按 `@Sensitive` 处理字段（`SensitiveJsonFieldProcessor`）。盘点出的“失败时输出原文”的路径：

| 路径 | 旧行为 |
|---|---|
| 没有 `SensitiveService` 实现（只有 `tuoyu-system` 提供） | 原样输出 |
| `isSensitive` 抛出异常 | 异常向上抛（500），尚不算泄露 |
| 脱敏函数遇到格式不符或长度不足的值（hutool 实现） | **原样返回**：没有 `@` 或 `@` 在第一位的邮箱、少于 7 位的手机号、少于 9 位的银行卡、长度不是 7 或 8 的车牌、单个字符的姓名…… |
| 注解用在非字符串字段上 | 原样输出 |
| 客户端用 `Accept` 选择 `application/xxx+json` 等类型 | `ResponseEnhancementAdvice` 只处理 `application/json`，**整个响应跳过脱敏** |

### 1.4 字段加密

`tuoyu-common-encrypt` 的 `@EncryptField`（MyBatis 拦截器，入库加密、出库解密）。盘点结果：

| 项 | 旧实现 |
|---|---|
| 算法 | BASE64（默认，只是编码）、AES、SM4、RSA、SM2 |
| AES / SM4 模式 | hutool 默认的 **ECB + PKCS5Padding**：没有 IV，相同明文得到相同密文（可以看出哪些行的值相同、可以做字典比对），没有完整性保护 |
| 密钥 | 16 / 24 / 32 个字符的原始字符串直接当作密钥，熵低；注解里可以写口令（密钥进代码） |
| 加密失败 | `EncryptedFieldProcessor` 捕获异常只记日志，**明文照常入库** |
| 解密失败 | 同上，密文原样交给业务 |
| 非字符串字段、静态内部类中的字段 | 静默跳过，**明文入库** |
| 以 `ENC_` 开头的值 | 视为已加密直接跳过：用户输入 `ENC_xxx` 就能让该值以明文入库，读取时又因无法解密而出错 |

## 2. 决定

### 2.1 上传：扩展名白名单 + 文件头校验

实现：`tuoyu-common-core` 的 `org.tuoyu.common.core.upload`（`FileType`、`UploadFileValidator`，自己实现的魔数表，不引入 Tika 等依赖），`tuoyu-resource` 的 `SysOssServiceImpl` 在写入对象存储之前校验。

**类型表**（`FileType`）：只有登记了文件头规则的类型才能进白名单。

| 类别 | 扩展名 | 规则 |
|---|---|---|
| 图片 | jpg、jpeg | `FF D8 FF` |
| | png | `89 50 4E 47 0D 0A 1A 0A` |
| | gif | `GIF87a` / `GIF89a` |
| | bmp | `BM`，且文件头中的 4 个保留字节为 0 |
| | webp | `RIFF....WEBP` |
| 文档 | pdf | `%PDF-` |
| | doc、xls、ppt | OLE2 复合文档 `D0 CF 11 E0 A1 B1 1A E1`（文件头无法再细分三者） |
| | docx、xlsx、pptx | ZIP 本地文件头，并且包含 `[Content_Types].xml` 与 `word/` / `xl/` / `ppt/`（按字节流搜索文件名，不解压，不受压缩炸弹影响） |
| 文本 | txt、csv | 开头 8KB 不含 NUL，除常见空白外的控制字符不超过 1%；不限定编码（UTF-8、GBK 都常见） |
| 压缩包 | zip、rar、7z、gz | 各自的文件头 |
| 音视频 | mp3（ID3 或帧同步字）、wav（`RIFF....WAVE`）、mp4（`ftyp` box） | |

HTML、SVG、XML、脚本、可执行文件没有可靠的文件头，**不登记，也就无法通过配置放行**。

**校验规则**（`UploadFileValidator.validate`）：

1. 文件名去掉客户端带上的路径与首尾空白，不能为空、不能含控制字符、不能以点结尾（Windows 会忽略结尾的点）；
2. 最后一个扩展名忽略大小写，必须在白名单中；
3. 中间的扩展名不能是可执行或可被服务器、浏览器解释的类型（`a.jsp.png`、`a.php.jpg`、`a.asp;.png` 拒绝；`report.2024.pdf` 放行），防止 Web 服务器按多扩展名解释；
4. 文件内容必须与扩展名相符，空文件拒绝；
5. 拒绝时的提示可直接展示给用户，例如“不允许上传 .svg 文件，允许的类型：jpg、png……”“文件内容与扩展名 .png 不符，请确认文件没有被改过扩展名”。

**存储**：对象键的扩展名取校验后的小写扩展名；写入对象存储与 `sys_oss.ext1` 的媒体类型由服务端按类型表认定，不采信客户端声明。下载接口同样按扩展名认定类型（类型表中没有的一律 `application/octet-stream`，覆盖旧数据），并加上 `X-Content-Type-Options: nosniff`。

**配置**：`tuoyu-resource.yml`

```yaml
tuoyu:
  upload:
    allowed-extensions: jpg,jpeg,png,gif,bmp,webp,pdf,doc,docx,xls,xlsx,ppt,pptx,txt,csv,zip,rar,7z,gz,mp3,wav,mp4
```

白名单中有不支持的类型时拒绝启动；Nacos 刷新后按新白名单校验。`ProductionConfigTest` 检查仓库配置中的白名单不含危险类型。

### 2.2 XSS：输出编码 + 富文本白名单

1. **删除全局过滤器**（`XssFilter`、`XssHttpServletRequestWrapper`、`XssProperties`、`FilterConfig` 与 `xss.*` 配置）。普通字段原样保存，由前端输出时转义（Vue 默认行为）。
2. **富文本字段**标注 `@RichText`（`tuoyu-common-web`），只能用于 String：
   - JSON 入参反序列化时按白名单清洗（`RichTextDeserializer`）；
   - JSON 响应输出前再清洗一次（`RichTextJsonFieldProcessor`），覆盖历史数据以及不经过 JSON 入参写入的数据。
3. **白名单**（`HtmlSanitizer`，基于 jsoup 的 `Safelist`，jsoup 为 MIT 协议，新增依赖 `org.jsoup:jsoup:1.23.1`）：
   - 标签：jsoup `relaxed` 白名单（段落、标题、列表、表格、引用、代码、图片、链接等）加上 `hr`、`s`、`del`、`ins`、`mark`、`figure`、`figcaption`；
   - 属性：不允许事件属性与 `style`（CSS 可以覆盖页面、伪造界面）；允许 `class`、链接的 `target`；
   - 地址：链接只允许 http、https、mailto 与相对地址；图片只允许 http、https、data 与相对地址；链接强制 `rel="noopener noreferrer nofollow"`；
   - 清洗结果再清洗不变（幂等）。
4. 目前没有字段标注。通知公告内容（`noticeContent`）在前端用多行文本框编辑、按文本展示，暂按纯文本处理：如果标注了 `@RichText`，纯文本中的 `&`、`<` 会被转义成实体、形如标签的内容会被去掉，用户再次编辑时看到的就是这些实体。前端改用富文本编辑器时，再在 `SysNoticeBo`、`SysNoticeVo` 的 `noticeContent` 上标注 `@RichText`，并且只对该字段使用 `v-html`。
5. `@Xss` 校验注解（用户账号、昵称、公告标题等）保留：它是“拒绝”而不是“修改”，与本决定一致。

**迁移说明**（使用本框架的业务代码）：

| 以前 | 现在 |
|---|---|
| 依赖全局过滤器删除标签 | 普通字段无需处理；前端按文本展示（不要用 `v-html`） |
| 富文本接口加入 `xss.excludeUrls` | 删除该配置，在 BO / VO 的字段上标注 `@RichText` |
| 富文本完全不清洗 | 自动按白名单清洗；需要 `style` 等更多标签属性时，评估后在 `HtmlSanitizer` 中调整并补测试 |
| Nacos 中的 `xss.enabled`、`xss.excludeUrls` | 不再生效，覆盖导入 `application-common.yml` 即可移除 |

不走 JSON 的入口（表单参数、Excel 导入、服务间调用）不会触发入参清洗，但响应输出时仍会清洗 `@RichText` 字段。服务端自己生成 HTML（邮件模板等）时，必须对拼入的用户数据做 HTML 转义。

### 2.3 脱敏失败闭合

1. `SensitiveStrategy.desensitize(String)`：脱敏函数抛异常，或者结果与原文相同（策略没有生效），一律返回固定长度的整体掩码 `******`；null 与空白原样返回。原有的 `desensitizer()` 保留，但输出一律用 `desensitize`。
2. `SensitiveJsonFieldProcessor`：
   - 没有 `SensitiveService` 实现时一律脱敏（只提示一次）；
   - `isSensitive` 抛异常时按“需要脱敏”处理；
   - 注解用在非字符串字段上，需要脱敏时输出 null（并提示一次）。
3. `ResponseEnhancementAdvice` 不再按协商出的内容类型跳过：凡是经过对象序列化的响应都执行增强（字符串、字节数组、资源类转换器由 `JsonValueEnhancer.supports` 排除）。
4. 增强过程中出现的异常向上抛出，由全局异常处理返回错误，不会退回输出未增强的原始对象。

### 2.4 字段加密：AES-GCM 与 SM4-GCM，失败闭合

1. **算法**：AES、SM4 写入一律使用 GCM 认证加密（`AeadFieldCipher`）。
   - AES-GCM 用 JDK 自带实现；SM4-GCM 用 BouncyCastle（已有依赖）的 `SM4Engine` + `GCMBlockCipher`，测试中用 GB/T 32907 的标准向量校验 SM4 分组算法；
   - 每次加密随机 12 字节 IV，128 位认证标签；附加数据（AAD）绑定格式版本与算法；
   - 密文格式：`ENC_v2:` + Base64(IV ‖ 密文 ‖ 标签)，Hex 编码时为 `ENC_v2x:` + Hex。旧格式（ECB）没有 `v2` 标记。
2. **密钥**：新增 `mybatis-encryptor.key`（环境变量 `TUOYU_FIELD_ENCRYPT_KEY`），Base64 编码的随机密钥，AES 为 16 / 24 / 32 字节（推荐 32），SM4 为 16 字节。生成：`java tools/secrets/GenerateEnv.java --field-key`（SM4 加 `sm4`）。字段加密默认关闭，因此生成 `.env` 时不自动生成这把密钥（密钥丢失则已加密数据无法恢复，应由使用者有意识地生成并备份）。
3. **旧数据兼容**：原 `mybatis-encryptor.password`（环境变量 `TUOYU_FIELD_ENCRYPT_LEGACY_PASSWORD`）与 `@EncryptField(password = ...)` 改为“旧版口令”，只用于解密 ECB 格式的旧密文；这些数据读出后在下次保存时写成新格式。只有旧口令、没有新密钥时，读可以、写报错。新密钥用单独的配置项，不复用 `password`，避免 32 个字符的旧口令恰好也是合法的 Base64 而被误当作新密钥。
4. **默认算法**改为 AES；BASE64 保留但启动时警告“这只是编码，不是加密”。开启加密而 `key` 缺失、不是 Base64 或长度不对时拒绝启动（信息中不含密钥）。
5. **失败闭合**（`EncryptedFieldProcessor`）：
   - 任一字段加密失败：已改动的字段恢复原值，抛出 `FieldEncryptionException`，SQL 不执行，明文不入库；
   - 解密失败：抛出 `FieldEncryptionException`，不把密文或半成品交给业务；
   - 异常信息只有类名与字段名，不含字段值；
   - `@EncryptField` 用在非字符串字段上时报错（启动扫描或首次使用时），静态内部类中的字段照常处理。
6. **“已加密”的判断**：以 `ENC_` 开头且能用当前配置解密才视为已加密；否则照常加密。GCM 密文无法伪造，用户输入 `ENC_xxx` 不能再绕过加密。
7. RSA、SM2 字段加密保持原实现（不推荐用于字段加密：非对称算法慢，且每个值有长度上限），同样受第 5 条失败闭合保护。
8. **代价：不能再按密文做等值查询。** ECB 是确定性加密，以前把带 `@EncryptField` 的实体作为查询参数（如 XML 中 `where phonenumber = #{phonenumber}`）时，入参被加密成相同的密文，可以匹配；随机 IV 之后同一明文每次的密文不同，这类查询查不到数据。确定性加密正是 ECB 泄露“哪些行的值相同”的原因，因此不提供确定性模式。确需按加密字段查找时，另加一列保存 HMAC-SHA256（独立密钥）的“盲索引”，按该列等值查询；需要时另立 ADR 实现。目前仓库内没有任何字段使用 `@EncryptField`，不受影响。

### 2.5 “密码传输支持 SM4”：不实现

评估结论：**有了接口加密之后不需要，不实现。**

1. 登录等接口已经由接口加密（`docs/adr/0001-接口加密.md`）整体加密：请求体（含密码）用一次性 AES-256-GCM 密钥加密，该密钥用服务端 RSA-OAEP-256 公钥封装，带时间窗口与 nonce 防重放。密码在传输中已有机密性与完整性保护，再单独对密码字段做 SM4 加密不增加安全性。
2. SM4 是对称算法，单独用于“密码传输”时，加密密钥必须出现在浏览器里，任何人都能从前端代码取出，等于没有加密——这正是接口加密要消除的旧方案问题（前端持有密钥）。要安全地使用 SM4，必须另有密钥协商（如 SM2），那就是在重新设计一套接口加密。
3. 真有国密合规需求时，正确做法是在接口加密协议中增加一个密码套件（SM2 封装 + SM4-GCM，按 `kid` / 算法标识协商），整套替换，而不是只对密码字段做 SM4。届时另立 ADR，并配套前后端测试向量。
4. 密码存储使用 BCrypt（不可逆），与传输加密无关，不受影响。

## 3. 前端需配合

1. 富文本只对标注了 `@RichText` 的字段使用 `v-html`（目前没有；通知公告内容改用富文本编辑器时会标注）；其他所有字段按文本展示。富文本编辑器不要依赖 `style` 属性（会被清洗掉），对齐、颜色等改用 `class` 或编辑器的语义标签。
2. 消息中心（`SysMessageVo.content`）的内容来自通知公告，也可能是业务推送的纯文本：一律按文本展示；如需展示公告原文，跳转到公告详情。
3. 上传组件：
   - 前端的 `accept` 与大小提示与 `tuoyu.upload.allowed-extensions` 保持一致；
   - 拒绝时直接展示后端返回的提示；
   - 上传 Blob（如裁剪后的头像）时必须带上带扩展名的文件名（如 `avatar.png`），否则会因缺少扩展名被拒绝；
   - 不要依赖上传响应中的 Content-Type 判断文件类型。

## 4. 升级影响

1. **需要覆盖导入 Nacos 配置**：`application-common.yml`（移除 `xss`、字段加密配置）、`tuoyu-resource.yml`（上传白名单）。
2. 以前能上传的 html、htm、svg、exe 等类型，以及内容与扩展名不符的文件，现在会被拒绝；已存储的这些文件不受影响，但下载时按 `application/octet-stream` 返回。公开桶中的旧对象仍带着上传时客户端声明的类型，如有必要请在对象存储中批量修正或迁移到私有桶。
3. 已开启字段加密的部署：把原 `mybatis-encryptor.password` 改填到 `TUOYU_FIELD_ENCRYPT_LEGACY_PASSWORD`，用 `--field-key` 生成新密钥填入 `TUOYU_FIELD_ENCRYPT_KEY`；数据库中加密字段的列宽需容纳新格式（明文 UTF-8 字节数 + 28 字节，再按 Base64 放大 4/3，加上 7 个字符的前缀）。旧数据全部重新保存后，删除旧口令。
4. 字段加密的默认算法由 BASE64 改为 AES：之前开启了加密且没有显式配置算法的部署，需要显式配置 `algorithm: BASE64` 才能读旧数据（建议借机迁移到 AES）。
5. 按加密字段做等值查询的业务代码需要改造（见 2.4 第 8 条）。
6. 无数据库结构变更。
