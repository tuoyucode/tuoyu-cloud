# ADR 0007：日志追踪与优雅停机

| 项 | 内容 |
|---|---|
| 状态 | **已采纳**（2026-10-31）：按本文实现并通过构建；第 8 节的 4 个取舍由维护者确认，均按当前做法 |
| 关联 | ADR 0005（`ContextPropagator`、本地调用代理、“需要容错的调用在调用处捕获异常”） |
| 适用 | 新模块 `tuoyu-common-observability`（原创编写，CONTRIBUTING.md 基本规则第 1 条）；`tuoyu-common-rpc`（`RemoteFallback`）；`tuoyu-common-dubbo`（超时与重试的默认值）；`tuoyu-common-core`（后台线程池停机）；`tuoyu-common-bus`（消息消费停机）；网关；所有服务的 logback 配置；Nacos 公共配置 |
| 红线 | `tuoyu-common-observability` 原创编写，不参考其他开源框架的代码。W3C Trace Context 是公开标准，本文只按标准实现格式 |

## 1. 背景

- 日志中没有请求标识：一次请求经过网关、auth、system，日志分散在多个服务中，无法串起来；单体中多个请求的日志交错，同样分不清；
- 停机顺序不对：Spring Cloud 在销毁 Bean 时才从 Nacos 注销，晚于 Web 容器停止接收请求，期间网关仍按缓存（默认 35 秒）把请求转发过来；Dubbo 在容器关闭事件中先于 Web 容器停止，处理中的 HTTP 请求再发起 Dubbo 调用会失败；后台线程池固定等 120 + 120 秒；消息总线消费线程直接中断；
- ADR 0005 删除了 Dubbo 的 mock 与 stub，改为在调用处 `try/catch`，几处写法各不相同，失败只有一行日志，没有计数，也不能告警。

## 2. 目标与非目标

**目标**

1. 所有服务（包括单体启动器）的每行日志带 traceId，格式只定义一处；
2. traceId 穿过网关、Dubbo、本地调用代理、`@Async`、`ThreadUtils` 的虚拟线程；响应头返回 traceId；
3. 两种部署方式都成立：单体中跨模块调用不经过 Dubbo，traceId 照样保持；
4. 停机时先下线、再排空请求，然后才停止 RPC、消息消费与线程池；等待时长可配置；
5. 需要容错的跨模块调用有统一的降级工具，两种部署方式语义一致，有日志与计数。

**非目标（1.1 做）**

- OpenTelemetry：span 的上报、采样、指标与日志的统一采集；
- 网关限流熔断、告警接入；
- 定时任务（SnailJob 执行器、`@Scheduled`）、消息消费（Redis Stream 总线、MQ）与 SSE / WebSocket 推送的入口链路：这些入口目前没有 traceId，任务内发起的 Dubbo 调用在提供方会各自开始新链路。

## 3. 日志追踪

### 3.1 格式：W3C `traceparent`

- 请求头 `traceparent: 00-<traceId 32 位十六进制>-<spanId 16 位十六进制>-<标志 2 位>`，按 W3C Trace Context 规范解析：版本 `ff` 无效；版本 `00` 长度必须是 55；全零的 traceId / spanId 无效；只接受小写十六进制。
- **不合法的值一律当作没有**，另起一条新链路，不拒绝请求，也不会把原值写进日志（防止日志伪造，例如在请求头中注入换行）。
- 选择 W3C 格式的理由：1.1 接入 OpenTelemetry 时，现有的服务、前端或外部系统产生的请求头可以直接被识别，日志中的 traceId 与链路系统中的一致，不需要改格式或做映射。没有采用自定义的 `X-Trace-Id` 请求头，避免 1.1 时出现两套标识。
- traceId 由网关（或第一个收到请求的服务）生成；每个执行位置（服务、异步线程）生成自己的 spanId，traceId 不变。标志位只原样传递，自己开始的链路为 `01`。
- 随机数用 `ThreadLocalRandom`：traceId 只用于关联日志，不是安全凭据。

### 3.2 入口

| 位置 | 做法 |
|---|---|
| 网关与各服务的 HTTP 入口 | `TraceFilter`（Servlet 过滤器，顺序 `HIGHEST_PRECEDENCE`，在请求大小限制、解密、网关日志之前）：采信合法的 `traceparent` 并继续这条链路，否则开始新链路；写入 MDC；把链路放在请求属性中；响应头 `X-Trace-Id` 返回 traceId；请求结束后恢复进入前的状态 |
| 异步分派、错误分派 | 同一个请求再次进入过滤器时沿用请求属性中的链路，SSE 等异步响应与错误页面的日志也是同一个 traceId |
| 网关转发 | `TraceHeadersFilter`（Gateway MVC 的请求头过滤器）用网关的链路覆盖 `traceparent` 后转发，客户端带来的不合法或不被采信的值不会到达下游；`TraceResponseHeadersFilter` 去掉下游返回的 `X-Trace-Id`（与网关写入的相同），避免重复 |
| 跨域 | 网关 CORS 允许请求头 `traceparent`，暴露响应头 `X-Trace-Id`，前端可以带上自己生成的链路，也可以读取 traceId 展示给用户 |

是否采信请求中的 `traceparent`：`tuoyu.trace.accept-incoming`，默认 `true`。各服务必须采信（网关转发时带给下游）；网关是入口，客户端可以指定 traceId，最坏的后果是把自己的请求与别人的 traceId 混在一起，不涉及权限，所以默认也采信，便于前端与外部系统关联。不希望客户端指定时，在网关的配置中设为 `false`。

### 3.3 跨边界透传：全部经由 `ContextPropagator`

`TracePropagator` 实现 ADR 0005 的 `ContextPropagator`，只透传一个字符串（键 `trace.parent`，值为 traceparent）。它排在其他透传实现之前恢复，租户签名校验失败等日志也带 traceId。

| 边界 | 微服务 | 单体 |
|---|---|---|
| 跨模块调用 | Dubbo 过滤器把它放进附件 `tuoyu-context`，提供方恢复（与租户、数据权限相同） | 本地调用代理在同一个线程中执行，MDC 天然存在，不需要透传 |
| `@Async` | `RpcAutoConfiguration` 的 `TaskDecorator` | 同左 |
| `ThreadUtils` 虚拟线程 | `ContextPropagators.wrap` | 同左 |

恢复时 traceId 不变、spanId 重新生成；**没有收到值时开始新链路**，保证 Dubbo 线程、异步线程中的日志总有 traceId。所有恢复都返回作用范围，结束时恢复执行前的 MDC：Dubbo 线程、线程池的线程被复用时不会带着上一个请求的 traceId（防止串号，有测试覆盖）。

### 3.4 日志格式：一个公共的 include 文件

- `tuoyu-common-observability` 中的 `logback-pattern.xml` 定义两个变量：`console.log.pattern`（控制台，彩色）与 `log.pattern`（文件），都带 `[%X{traceId:-}]`；
- 各服务的 `logback-spring.xml` 与 `logback-common.xml` 删除自己的格式定义，在最前面 `<include resource="logback-pattern.xml"/>`；修改格式只改这一处；
- MDC 键为 `traceId`、`spanId`，与 Micrometer Tracing 的约定相同；Logstash 编码器默认输出全部 MDC，日志收集中自动多出这两个字段；
- 单体启动器同样引用它（用法见第 7 节）。

## 4. 优雅停机

### 4.1 问题

Spring 关闭容器的顺序是：发布 `ContextClosedEvent` → 按阶段停止各组件（其中有 Web 容器的优雅停机）→ 销毁 Bean。现状中：

- Dubbo 在 `ContextClosedEvent` 中注销并关闭（Dubbo 自带的监听器，排在最后）——早于 Web 容器停止；
- Spring Cloud 的服务注册在销毁 Bean 时才注销——晚于 Web 容器停止接收请求；
- 网关的负载均衡缓存默认 35 秒，注销后仍按缓存转发。

### 4.2 决定：先下线、再排空，再停止其他组件

`GracefulShutdownCoordinator`（`ContextClosedEvent` 的监听器，最先执行，只处理本容器、只执行一次）：

1. **健康检查下线**：就绪状态改为 `REFUSING_TRAFFIC`，开启就绪探针（`management.endpoint.health.probes.enabled=true`）后 `/actuator/health` 与 `/actuator/health/readiness` 返回 503，反向代理、Kubernetes 据此摘除本实例；
2. **注册中心下线**：执行全部 `OfflineAction`。内置一个：调用 Spring Cloud 服务注册的 `stop()`，从 Nacos 注销（之后 Spring Cloud 自己的销毁逻辑不会重复注销）。业务可以注册自己的 `OfflineAction`；动作失败只记录警告；
3. **等待** `tuoyu.shutdown.offline-delay`（公共配置默认 5 秒）：网关的负载均衡缓存（改为 3 秒）与反向代理的健康检查需要时间发现本实例已下线，这段时间内**仍正常处理新到的请求**；
4. **排空 HTTP 请求**：Web 容器停止接收新请求，等待处理中的请求完成，最多 `tuoyu.shutdown.timeout`（默认 30 秒）。此时 Dubbo 尚未关闭，处理中的请求仍可发起 Dubbo 调用。

之后按 Spring 原有的顺序：Dubbo 注销并等待处理中的调用（`dubbo.application.shutwait`，默认 10 秒）→ 各组件按阶段停止（每阶段最多 `spring.lifecycle.timeout-per-shutdown-phase`，与 `tuoyu.shutdown.timeout` 相同）。Spring 自身的 Web 容器优雅停机阶段会再执行一次，此时已没有请求，立即完成。

**Dubbo 只由 Spring 关闭**（2026-11-03 补充）：Dubbo 默认还会注册自己的 JVM 停机钩子，它与 Spring 的停机钩子同时开始，只等待 `shutwait` 让 Spring 关闭 Dubbo，超时就自行销毁。上面第 1 ~ 4 步（加上 Nacos 客户端的停机等待）通常超过 10 秒，Dubbo 会在请求排空期间被提前销毁——排空中的请求发起的 Dubbo 调用失败，Spring 关闭 Dubbo 时还会报 `ExtensionDirector is destroyed`（本机联调时发现）。所以 `tuoyu-common-dubbo` 在配置加载阶段设置系统属性 `dubbo.shutdownHook.listenIgnore=true`（`DubboShutdownHookEnvironmentPostProcessor`；Dubbo 创建应用模型时就读取它，早于读取 Spring 配置，只能用系统属性；已显式设置时不覆盖），不注册 Dubbo 自己的钩子。

| 组件 | 停机方式 |
|---|---|
| Web 容器（Jetty） | `server.shutdown: graceful`；排空见上 |
| Dubbo | Dubbo 自带：注销 → 等待 `shutwait` → 关闭 |
| `@Async`、Spring 定时任务 | `spring.task.execution/scheduling.shutdown.await-termination: true`，最多 `tuoyu.shutdown.timeout` |
| 后台任务线程池（`scheduledExecutorService`） | 先 `shutdown` 等待最多 `tuoyu.shutdown.timeout`，超时再中断（原来固定 120 + 120 秒） |
| 消息总线（Redis Stream 消费） | 停止读取新消息，等待正在处理的一批确认，最多 `spring.cloud.bus.redis.shutdown-timeout`（默认 10 秒）后才中断；先停止再移除消费者（移除消费者会丢弃它名下未确认的消息）。未确认的消息由其他实例按 `claim-idle-timeout` 认领 |
| SnailJob 执行器、RabbitMQ 等 | 依赖库自身的生命周期，1.0 不改 |

**部署要求**：容器的停止宽限期（`docker stop -t`、compose 的 `stop_grace_period`、Kubernetes 的 `terminationGracePeriodSeconds`）应不少于 `offline-delay + timeout + shutwait + 10 秒`（默认约 55 秒），否则会被强制结束。Docker 默认只有 10 秒。

单体：没有注册中心与 Dubbo，第 1、3、4 步照常执行（反向代理按健康检查摘除）。

### 4.3 配置

| 配置项 | 环境变量 | 默认值 | 位置 |
|---|---|---|---|
| `tuoyu.shutdown.offline-delay` | `TUOYU_SHUTDOWN_OFFLINE_DELAY` | 5s（代码中为 0，测试不等待） | `application-common.yml` |
| `tuoyu.shutdown.timeout` | `TUOYU_SHUTDOWN_TIMEOUT` | 30s | 同上；`spring.lifecycle.timeout-per-shutdown-phase` 与任务执行器的等待时长引用它 |
| `tuoyu.shutdown.enabled` | — | true | 代码默认 |
| `dubbo.application.shutwait`（毫秒） | `TUOYU_DUBBO_SHUTDOWN_WAIT` | 10000 | `application-common.yml` |
| `server.shutdown` | — | graceful | 同上 |
| `management.endpoint.health.probes.enabled` | — | true | 同上 |
| `spring.cloud.loadbalancer.cache.ttl` | — | 3s | `tuoyu-gateway.yml`（须小于 offline-delay，`ProductionConfigTest` 检查） |

## 5. 跨模块调用的统一降级

### 5.1 约束

ADR 0005 已删除 Dubbo 的 mock 与 stub；业务模块与 api 模块中不能出现 Dubbo（ArchUnit）。降级必须在两种部署方式下语义相同，所以不能依赖 Dubbo 的特性，只能在调用处。

### 5.2 决定：`RemoteFallback`（`tuoyu-common-rpc`，不依赖 Dubbo）

```java
String url = RemoteFallback.call("resource.file-url", () -> remoteFileService.selectUrlByIds(ids), "");
RemoteFallback.run("resource.message.welcome", () -> remoteMessageService.publishMessage(userIds, text));
List<RemoteFile> files = RemoteFallback.callOrElseGet("resource.file-url", () -> ..., List::of);
```

- **在调用线程中执行，不切换线程**：登录、租户、数据权限等上下文与直接调用完全相同（登录上下文在线程间不透传，切换线程会改变语义）；
- 任何 `RuntimeException` 触发降级：提供方的业务异常、微服务中的超时与网络错误、单体中提供方抛出的异常；`Error` 不降级；
- **超时**：微服务中由 Dubbo 的调用超时负责（默认 3 秒，`TUOYU_DUBBO_TIMEOUT`），超时异常触发降级；单体中是进程内调用，没有超时（ADR 0005 第 3.5 节），降级只针对失败。工具本身不做超时控制：要做超时就要切换线程，与上一条冲突；
- **日志**：同一名称每分钟最多一条 WARN（附带期间的失败次数），其余为 DEBUG，依赖的服务故障时不刷屏；
- **计数**：`RemoteFallback.counts()`；有 Micrometer 时记入指标 `tuoyu.remote.fallback`（标签 `call`，Prometheus 中为 `tuoyu_remote_fallback_total`），可以告警；
- 名称必填，建议 `提供方模块.用途`。

### 5.3 哪些调用降级，哪些必须让异常原样到达调用方

| 类别 | 调用 | 处理 |
|---|---|---|
| **降级**：结果可有可无，失败不应影响主流程 | 登录后推送欢迎消息（auth `TokenController`，`resource.message.welcome`） | `RemoteFallback.run` |
| | 发布通知公告后推送（system `SysNoticeController`，`resource.message.notice`）：公告已保存，推送失败原来会使请求返回 500 | `RemoteFallback.run` |
| | 工作流办理后发送站内消息、邮件（workflow `FlwCommonServiceImpl`，`resource.message.workflow`、`resource.mail.workflow`） | `RemoteFallback.run`（原来是包住整个分支的 `catch (Exception)`） |
| | 文件 ID 翻译为访问地址（translation `OssUrlTranslationImpl`，`resource.file-url`） | `RemoteFallback.call`，失败时为空 |
| **不降级**：异常原样到达调用方 | 权限、数据权限（`RemotePermissionService`、`RemoteDataScopeService`） | 降级会放宽或收窄权限，必须失败 |
| | 租户（`RemoteTenantService`）、登录、注册、第三方账号绑定、客户端校验 | 安全相关，必须失败 |
| | 写入业务数据的调用（用户、角色、流程办理人等） | 调用方需要知道结果；不能重试（见 5.4） |
| | 字典（`RemoteDictService`） | 字典值参与业务判断，不能当作空 |
| | 用户名、昵称、部门名翻译 | 目前不降级（与升级前相同）。它们主要在 system 内部，是本地调用；如需降级，按上表用 `RemoteFallback.call` |
| | 操作日志、登录日志的保存（`RemoteLogService`） | 在异步监听器中执行，失败由异步异常处理记录错误；不静默降级，1.1 考虑本地落盘重试 |

新增的跨模块调用默认**不降级**；确定结果可有可无时才用 `RemoteFallback`，并补充到上表。

### 5.4 Dubbo 的超时与重试默认值（`tuoyu-common-dubbo`）

- 超时：`dubbo.consumer.timeout: ${TUOYU_DUBBO_TIMEOUT:3000}`，在 `common-dubbo.yml` 中统一维护（原来写在 Nacos 公共配置中，已移除）；
- **不重试**：框架无法判断接口是否幂等，超时的调用可能已在提供方执行，重试会重复写入。`DubboRemoteReferenceFactory` 创建的远程引用固定 `retries=0`，`dubbo.consumer.retries` / `dubbo.provider.retries` 也为 0。单体中本来就没有重试，两种方式一致。

## 6. 模块与依赖

| 模块 | 内容 |
|---|---|
| `tuoyu-common-observability`（新，原创） | `trace`：`TraceParent`、`TraceContext`、`TraceFilter`、`TracePropagator`、`TraceProperties`；`shutdown`：`GracefulShutdownCoordinator`、`OfflineAction`、`GracefulShutdownProperties`；`logback-pattern.xml`。除 Spring Boot 外的依赖都是可选的（core、spring-web、Servlet、web-server、spring-cloud-commons），监控中心、SnailJob 服务端等不带 core 的服务也能使用，不会因此加载 core 的自动配置 |
| 依赖它的模块 | `tuoyu-common-web`（因而所有业务服务）、网关、`tuoyu-monitor`、`tuoyu-snailjob-server`、`tuoyu-snailai-server` |
| `tuoyu-common-rpc` | `RemoteFallback`；可选依赖 `micrometer-core`（Apache-2.0，版本由 Spring Boot 管理） |

新增依赖：无新的第三方库（`micrometer-core` 已在各服务中）。

## 7. 单体启动器的用法

- 依赖 `tuoyu-common-web`（已带 observability）即可获得 `TraceFilter`、`TracePropagator`、停机协调；
- logback 配置的最前面：

```xml
<include resource="logback-pattern.xml"/>
<!-- 之后使用 ${console.log.pattern}（控制台）与 ${log.pattern}（文件）；或者直接 include logback-common.xml（文件输出，内部已引用格式） -->
```

- 跨模块调用由本地调用代理在同一线程中执行，traceId 自动保持（`MonolithTracePropagationTest`）。

## 8. 取舍（2026-10-31 维护者确认，均按当前做法）

| # | 问题 | 决定 | 理由 |
|---|---|---|---|
| D1 | 网关是否采信客户端的 `traceparent` | **采信**；不合法时另起新链路，原值不写进日志。需要时可在网关配置 `tuoyu.trace.accept-incoming: false` 关闭 | 前端可以自己生成 traceId，用户报错时直接据此查后端日志；外部指定 traceId 只影响日志关联，不涉及权限 |
| D2 | 下线等待默认 5 秒、网关负载均衡缓存 3 秒 | **保持** | 下线后给网关留出发现实例变化的时间，避免停机时出现 503；本地 `GenerateEnv` 生成的 `.env` 中下线等待为 0，不影响开发时重启 |
| D3 | 名称翻译（用户名、昵称、部门名）是否降级 | **不降级**，提供方不可用时请求报错（与改造前相同）；文件地址翻译已降级 | 名称是业务数据的一部分，缺失时应当让人知道，降级会掩盖故障、让数据看起来缺字段 |
| D4 | 定时任务、消息消费入口的 traceId | **推迟到 1.1**，与 OpenTelemetry 全量接入一起做 | 避免先写一套入口埋点、接入 OpenTelemetry 时再替换 |

## 10. 后果

- 日志格式变化：每行多一个 `[traceId]`（没有时为 `[]`）。按固定列解析日志的脚本需要调整；
- 停机变慢：默认多等 5 秒下线时间，最长约 55 秒；部署时需要调大容器的停止宽限期；
- 发布通知公告时推送失败不再返回 500（公告已保存）；
- 1.1 接入 OpenTelemetry 时，可以用它的上下文替换 `TraceContext`，`traceparent` 格式与 MDC 键不变。
